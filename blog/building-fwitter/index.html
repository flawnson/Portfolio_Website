Building Fwitter: a personal microblog with AI-powered social syndication

engineeringphpai

How I built a microblog on my own domain that automatically routes posts to X, Bluesky, and Threads using Gemini AI.

For the longest time I've had this mental block that prevented me from posting online.

Every time I have a Twitter-thought; the activation energy I need to actually open the app, write the post, and post it feels abnormally high. I'm not on social media often; I don't doomscroll or even upvote/like/<insert your mechanic here> posts, and I almost never leave comments/replies.

Then there's the fact that these platforms have a clear bias towards certain sentiments, styles, and opinions. How do I, as a social-media minimalist, navigate these trecherous waters and build my social capital?

So to fix my problems, I built Fwitter: a personal microblog that lives on my domain, stores everything in my own database, and syndicates to social platforms automatically. The interesting part is the routing: instead of cross-posting the same thing everywhere, I use Gemini (because they have a generous free tier) to decide which single platform each fweet is best suited for, then route the content to the platform using their API.

Here's how it's built.

The design philosophy

When I started building Fwitter, I hoped it would help reduce the friction of posting my thoughts online more. To that end, it has succeeded beyond my expectations, and I think it's safe to say I've developed a habit of opening and posting every day. This meant that I needed my own database, which was easy to set up on MySQL, cPanel's default SQL db. Even now it's the source of truth for my posts, and routing only happens after the post has successfully written to database.

In Fwitter, a post exists the moment it's written to my database. Everything after that — Gemini routing, publishing to X, publishing to Bluesky, publishing to Threads — is bonus. Those operations are fire-and-forget. If they fail, the post still exists. If they succeed, great. Social platforms are distribution, not storage.

This also means the system degrades gracefully. If Gemini is down, the post still gets saved and syndication is skipped. If the X API is flaky, the post still exists on Fwitter. The only failure mode that matters is the database write.

The database

The schema is deliberately minimal:

CREATE TABLE micro_posts (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    body TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    is_published TINYINT(1) NOT NULL DEFAULT 1
);

That's it. No syndication status column, no external platform IDs stored back, no retry queue. Syndication results are logged to error_log for debugging, but they're not persisted in the schema. This might change if I add structured retry tracking, but the simplicity of not caring about syndication at the schema level has been worth it. I've never needed to query "which posts failed to publish to Bluesky" — and if I did, I'd add the column then.

Using BIGINT UNSIGNED for the ID is a habit. With AUTO_INCREMENT it doesn't matter in practice, but IDs leak information about volume and I'd rather not have the ID space cap out unexpectedly if this runs for a long time. The is_published flag exists for future soft-delete support but isn't currently used in any query.

The API

The backend is a single PHP file. I'm hosting on cPanel with shared PHP hosting, which means no background workers, no job queues, no Redis. Just PHP with PDO and curl. That constraint turned out to be clarifying: you stop reaching for architecture and start thinking about what you actually need.

Authentication is an admin token passed as an X-Admin-Token header, compared with hash_equals() to prevent timing attacks. The API supports GET for reading the feed and POST for creating posts. GET is public; POST requires the token.

CORS is handled with an explicit allowlist: flawnson.com and localhost variants for development. The Vary: Origin header is set so caches don't serve one origin's response to another.

Pagination on the read side uses a before_id cursor rather than offset-based pages. Offset pagination is simpler to implement but gets unstable under concurrent writes: if a new post arrives between page 1 and page 2, offset-based pagination either skips an item or shows it twice. ID cursors don't have this problem. The query fetches limit + 1 rows — if you get back more than limit, there's a next page, and you return the last ID as the cursor.

Routing with Gemini

Deciding which platform to post to is the most interesting part of the whole system.

X, Bluesky, and Threads have genuinely different characters. X rewards sharp, opinion-dense takes — startup energy, systems thinking, technical insight in as few words as possible. Bluesky has a softer, more reflective community: creative work, books, thoughtful observations, writing that's a little more comfortable being uncertain. Threads is casual and warm — fitness updates, internet culture, relatable moments, the kind of thing you'd say to a friend.

Posting the same thing verbatim to all three is lazy. But manually picking a platform for every post introduces enough friction that you stop posting. So I gave the routing decision to Gemini.

The model gets the post text and a short description of each platform's character, and it outputs exactly one word:

You are a content routing agent for a personal microblog.
Given a post, choose the single best platform for it.

Platform guide:
- x: authority, startups, technical ideas, AI, systems thinking, founder energy.
  Sharp, high-signal, concise.
- bluesky: creativity, music, books, artistic observations, thoughtful reflection.
  Curious, nuanced, emotionally honest.
- threads: lifestyle, fitness, food, internet culture, casual daily life, warm humor.
  Casual, friendly, cozy.

Output EXACTLY ONE of: x, bluesky, threads
No punctuation. No explanation. No extra words.

The model is gemini-2.5-flash with temperature 0 (deterministic), thinking budget 0 (fast and cheap on 2.5 models), and max output tokens of 16. The response is validated against the three expected values; anything else is treated as a routing failure and syndication is skipped.

This is one of the more practical AI integrations I've built because it's not trying to generate anything creative — it's just making a classification decision that I'd otherwise have to make manually. The cost per call is a fraction of a cent. The latency is under a second. And it gets the routing right often enough that I rarely notice when it doesn't.

One thing I noticed: giving the model tie-breaker rules helped a lot. Serious or professional → X. Thoughtful or artistic → Bluesky. Casual or social → Threads. Without tie-breakers, borderline posts tended to cluster on X because it's listed first.

Social platform integrations

Each platform has a completely different API design and auth story, which is either charming or exhausting depending on the day.

X: OAuth 1.0a

X is the only platform that required I purchase credits to use their API. At the time of writing it costs $0.015 per create request (and .20 to create with a URL in the content).

X uses OAuth 1.0a with four credentials: consumer key, consumer secret, access token, and access token secret. This is the older standard. Every request is signed with HMAC-SHA1: you collect your parameters, sort them, percent-encode them, build a signature base string from the method + URL + parameters, and compute the signature using a key derived from your consumer and token secrets. It's verbose to implement but the logic is deterministic and easy to test.

The endpoint is straightforward:

POST https://api.x.com/2/tweets
Content-Type: application/json
Authorization: OAuth oauth_consumer_key="...", oauth_nonce="...", ...

{"text": "your post here"}

The main benefit of OAuth 1.0a over a simple bearer token is explicitness: these credentials are tied to exactly one account and one application. There's no ambiguity about which account a post comes from, and the signing overhead is the cost of that guarantee.

Bluesky: AT Protocol

Bluesky uses the AT Protocol, which is newer and considerably cleaner to work with. Auth happens per-request: you post your handle and app password to /xrpc/com.atproto.server.createSession, which returns an access JWT and a DID (decentralized identifier). You then use the JWT to create a record in the right collection.

POST https://bsky.social/xrpc/com.atproto.repo.createRecord
Authorization: Bearer {accessJwt}

{
  "repo": "{did}",
  "collection": "app.bsky.feed.post",
  "record": {
    "$type": "app.bsky.feed.post",
    "text": "your post here",
    "createdAt": "2026-05-11T12:00:00Z"
  }
}

Creating a new session on every post means there's no persistent token to store or refresh. App passwords are long-lived; the session they generate is ephemeral. This makes the integration stateless: if the server restarts between posts, nothing breaks. The $type field and the ISO createdAt are required by the protocol; omitting either produces a validation error.

Threads: the two-step dance

Threads was by far the most annoying to set up. There were multiple steps and it was generally not very well-documented. My biggest problem is the lack of clarity around what was under Meta's jurisdiction vs Instagram and Threads. My struggles here partly inspired me to write this blog in the first place.

Threads uses Meta's Graph API and requires two requests per post. First you create a container:

POST /{userId}/threads
media_type=TEXT&text=your+post+here&access_token={token}

That returns a creation ID. Then you publish it:

POST /{userId}/threads_publish
creation_id={creationId}&access_token={token}

The two-step design apparently exists to support future batch operations or pre-scheduling, but for plain text posts it's just extra latency. The more annoying thing is the access token: it's long-lived but expires after roughly 60 days, and you have to refresh it proactively. Of the three integrations, Threads is the one I have to think about the most because of that expiry. The refresh endpoint is simple — a GET request with your current token — but it's a maintenance task that the others don't require.

Non-blocking syndication

Here's where the shared-hosting constraint got interesting.

The full syndication chain — Gemini routing plus a social media API call — can take a few seconds. If I block the HTTP response on all of that, posting feels slow even though the actual write succeeded before any of it started. The fix is to respond to the client as soon as the database write is done, then syndicate afterwards.

In PHP-FPM, which is what cPanel runs, there's a function called fastcgi_finish_request() that flushes the HTTP response to the client and closes the connection while letting the PHP process continue executing. Combined with ignore_user_abort(true) at the top of the file, this gives you a clean "respond now, finish work later" pattern:

$postId = (int)$pdo->lastInsertId();

http_response_code(201);
header('Content-Type: application/json');
$responseJson = json_encode(["ok" => true, "id" => $postId, "syndication" => "pending"]);
header('Content-Length: ' . strlen($responseJson));
echo $responseJson;

if (function_exists('fastcgi_finish_request')) {
    fastcgi_finish_request(); // client gets their 201 here
} else {
    ob_flush();
    flush();
}

run_syndication_safely($body, $postId); // runs after the client is gone
exit;

The Content-Length header is important: without it, some proxies and clients will buffer the response and wait for the connection to close before delivering it, defeating the whole point. Setting it explicitly tells the client exactly when the response body ends, so it can process the response without waiting for the underlying connection to drop.

The client sees an instant 201. Gemini and the social platforms run in whatever time they take. From the outside it feels like a fast write; the syndication is genuinely invisible.

The frontend

This section is a placeholder — I'll write it up properly once I've had more time with the frontend code.

The public-facing side of Fwitter is a read-only infinite-scroll feed at /fwitter/. Posts are fetched from the API in pages of 20 using an IntersectionObserver that watches a sentinel element at the bottom of the feed. When the sentinel enters the viewport, the next page loads. The feed is purely chronological, most recent first, with relative timestamps ("2 hours ago") computed client-side from the ISO strings the API returns.

Reflections

A few things stand out after building and running this for a while.

The AI routing decision is the most interesting thing in the whole stack. Not because it's technically impressive — it's a classification call with a 16-token output — but because it changes how I write. Knowing that the content itself will determine where a post lands makes me think differently about each one. I'm not asking "where should I put this?" I'm asking "what kind of post is this?" That's a better question.

The database-first philosophy turned out to be load-bearing in ways I didn't fully anticipate. There have been a few times where syndication failed silently — Gemini returned something unexpected, a platform was briefly down — and I didn't notice for days because my posts were still there on Fwitter. The social platforms are nice to have, but I genuinely don't depend on them anymore in the way I used to.

The shared-hosting constraint was probably the most clarifying technical decision, even though it wasn't really a decision — it's just where the site lives. Not having access to a queue or background workers forced me to think carefully about what actually needs to block on what. fastcgi_finish_request() is one of those PHP features that feels like a hack until you realize it's exactly the right tool for this use case. A queue would have been more correct in a distributed sense; this is more correct for the actual problem.

The thing I'd change: I'd add a syndication_status column to the database and log the platform result back after each syndication run. Right now, whether a post made it to X or Bluesky is observable only through error_log, which is not a great debugging experience. Tracking status in the schema would make it easy to build a small retry UI and would give me better visibility into which platform is flaky and when.
